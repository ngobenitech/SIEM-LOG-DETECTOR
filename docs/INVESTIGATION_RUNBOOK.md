# SSH Authentication Alert Runbook

## Purpose

Use this runbook for alerts generated by `SSH-BF-001`, `SSH-PS-002`, and
`SSH-SAF-003`. The goal is to validate the signal, establish scope, and make an
evidence-based escalation decision.

## Required alert fields

Confirm that the alert contains:

- rule ID and severity;
- affected hostname or hostnames;
- source address;
- targeted username or list of usernames;
- first and last observed timestamps;
- matching event count;
- raw log evidence;
- thresholds active during analysis.

If any field is missing, record the limitation before reaching a conclusion.

## Triage workflow

### 1. Validate the detection

1. Review the raw evidence and confirm that each record is an SSH authentication
   event.
2. Confirm that timestamps fall inside the configured window.
3. Check that source addresses and usernames were parsed correctly.
4. Confirm the event was not generated by a known test or maintenance window.

### 2. Identify the source

1. Determine whether the address is internal, external, VPN, NAT, a jump host, or
   an approved scanner.
2. Review firewall, VPN, proxy, and threat-intelligence context where available.
3. Check whether the same source targeted other hosts or services.

### 3. Review the accounts

1. Identify whether any targeted account is privileged, shared, dormant, or a
   service account.
2. Search for successful authentication after the detected failures.
3. Review recent password resets, lockouts, MFA activity, and support tickets.
4. Contact the account owner for `SSH-SAF-003` when the login cannot be validated
   from available telemetry.

### 4. Scope post-authentication activity

For a suspicious successful login, examine:

- session start and end;
- commands and shell history where collection is lawful and available;
- `sudo`, `su`, group, and permission changes;
- new users, SSH keys, cron jobs, or services;
- outbound connections and file transfers;
- endpoint alerts and relevant process ancestry.

### 5. Decide and act

| Finding | Classification | Action |
|---|---|---|
| Approved scanner or documented test | Benign positive | Record owner and ticket; tune only if recurring |
| Legitimate user error with matching context | Benign positive | Close with evidence |
| Repeated unauthorized failures, no success | Attempted intrusion | Block/rate-limit as appropriate and monitor accounts |
| Successful login cannot be validated | Suspicious | Escalate and increase monitoring |
| Unauthorized successful login or malicious activity | Confirmed incident | Contain source/session, protect credentials, preserve evidence, follow incident process |

## Containment considerations

Containment should match organizational authority and impact:

- terminate an unauthorized session;
- block or rate-limit the source;
- disable or reset the affected account;
- revoke active sessions and replace exposed SSH keys;
- isolate a compromised endpoint;
- preserve relevant logs before retention or rotation removes them.

Avoid permanent source blocking without considering shared VPN, NAT, and cloud
addresses.

## Closure record

Document:

- alert ID and rule;
- analyst and timestamps;
- evidence reviewed;
- source and account ownership;
- related systems and alerts;
- classification and confidence;
- actions taken;
- false-positive cause and tuning recommendation, if applicable.
