# SSH Authentication Alert Investigation Runbook

## Purpose

This runbook provides a repeatable triage and escalation workflow for alerts
generated by `SSH-BF-001`, `SSH-PS-002`, and `SSH-SAF-003`. Follow each step
in order unless the organization's incident-response policy specifies a faster
path. Record findings in the ticketing system as you proceed.

## Prerequisites

Before starting, confirm you have access to:

- SIEM query interface (Splunk, Elastic, or equivalent);
- asset inventory or CMDB;
- threat-intelligence platform (AbuseIPDB, VirusTotal, or internal);
- VPN, firewall, and proxy logs;
- identity-provider and MFA logs;
- endpoint telemetry (EDR, process audit, shell history) where available;
- on-call rotation and escalation contacts.

## Alert validation checklist

Every alert must contain the following fields. If any field is missing, record
the gap and do not reach a conclusion until the missing data is sourced.

- [ ] `rule_id` and `severity`
- [ ] `source_ip`
- [ ] `hostname` or `hostnames`
- [ ] `username` or `unique_users`
- [ ] `first_seen` and `last_seen` timestamps
- [ ] `event_count`
- [ ] `evidence` (raw log lines)
- [ ] Active `configuration` thresholds at the time of detection

If the alert was generated from a truncated or rotated log file, note the
retention gap before concluding.

## Step 1: Validate the detection

### 1.1 Confirm raw evidence

Open each raw log line listed in the alert's `evidence` field and verify:

- the line is an SSH authentication record (starts with a timestamp and
  contains `sshd`);
- the action is `Failed password` or `Accepted password` / `Accepted publickey`;
- the parsed `source_ip`, `source_port`, and `username` match the raw text.

### 1.2 Confirm timing

Check that all events fall inside the configured correlation window.

**Splunk SPL:**
```spl
index=linux sourcetype=ssh
| search _raw IN ("<raw_evidence_line_1>", "<raw_evidence_line_2>", "...")
| table _time hostname src_ip username action source_port
| sort _time
```

If events fall outside the window, the alert may be a detector bug. Record the
finding and escalate to the engineering team.

### 1.3 Confirm the source is not a known test

Cross-reference the `source_ip` and time range against:

- change-management tickets;
- vulnerability scanner schedules;
- penetration-test windows;
- scheduled maintenance.

**Splunk SPL for maintenance windows:**
```spl
index=main sourcetype=maintenance
| search start_time<=<first_seen> end_time>=<last_seen>
| table change_ticket owner start_time end_time scope
```

## Step 2: Identify the source

### 2.1 Classify the address

Determine whether the `source_ip` is:

- internal corporate;
- VPN or remote-access concentrator;
- NAT gateway;
- known jump host;
- approved scanner or RMM tool;
- external / unknown.

**AbuseIPDB enrichment:**
```bash
curl -G https://api.abuseipdb.com/api/v2/check \
  --data-urlencode "ipAddress=<source_ip>" \
  -H "Key: <YOUR_ABUSEIPDB_API_KEY>" \
  -H "Accept: application/json"
```

Parse the JSON response and record:

- `abuseConfidenceScore` (> 50 is suspicious, > 80 is high confidence);
- `countryCode`;
- `usageType` (e.g., `Data Center`, `ISP`, `Government`);
- `totalReports`;
- `lastReportedAt`.

If `abuseConfidenceScore` is above 80, treat the source as hostile until
validated otherwise.

### 2.3 Check for broader targeting

Search for the same source IP targeting other hosts or services in the same
time window.

**Splunk SPL:**
```spl
index=linux sourcetype=ssh
| search src_ip="<source_ip>" earliest=<first_seen> latest=<last_seen>
| stats count by hostname, username, action
| sort -count
```

If the source touched more than five hosts or ten accounts, widen the
investigation scope and consider `SSH-BF-001` plus `SSH-PS-002` as a combined
campaign.

## Step 3: Review the accounts

### 3.1 Identify account criticality

For every `username` or entry in `unique_users`, determine whether the account
is:

- privileged (`root`, `admin`, `domain admin`, service account with sudo);
- dormant (no successful login in 90+ days);
- shared (multiple people know the password);
- a service account with a static password.

Query the identity provider for last-successful authentication and group
membership.

**Splunk SPL for identity-provider logins:**
```spl
index=aad sourcetype=SigninLogs
| search UserPrincipalName="<username>@<domain>"
| stats earliest(_time) as first_success latest(_time) as last_success by UserPrincipalName, AppDisplayName, Location
```

### 3.2 Search for post-failure success

For `SSH-SAF-003`, confirm that a successful authentication occurred and
examine what happened after login.

**Splunk SPL:**
```spl
index=linux sourcetype=ssh
| search src_ip="<source_ip>" username="<username>" hostname="<hostname>"
| search action="Accepted password" OR action="Accepted publickey"
| table _time action source_port
| sort _time
```

If no success was found outside the detector's window, widen the search by
±30 minutes to account for clock drift or delayed log forwarding.

### 3.3 Check credential hygiene

Review:

- recent password resets for the affected account;
- account lockout or MFA re-enrollment events;
- support tickets mentioning the account or source IP.

**Splunk SPL for lockouts:**
```spl
index=aad sourcetype=Audit
| search Operation="User account locked" TargetUserName="<username>"
| table _time TargetUserName Computer
| sort -_time
```

## Step 4: Scope post-authentication activity

If the investigation confirms a suspicious or unauthorized successful login,
examine session activity.

### 4.1 Session timeline

**Splunk SPL for SSH session start:**
```spl
index=linux sourcetype=sshd
| search action="Accepted password" OR action="Accepted publickey"
| search src_ip="<source_ip>" username="<username>"
| table _time hostname pid session_id
| sort _time
```

### 4.2 Command execution

**Splunk SPL for shell commands:**
```spl
index=linux sourcetype=auditd
| search hostname="<hostname>" uid="<uid_of_username>"
| table _time exe args cwd pid ppid
| sort _time
```

If auditd is not available, check shell history files.

### 4.3 Privilege changes

**Splunk SPL for sudo/su:**
```spl
index=linux sourcetype=auth
| search (action="sudo" OR action="su")
| search hostname="<hostname>" username="<username>"
| table _time action user sudo_user tty
| sort _time
```

### 4.4 Persistence and lateral movement

Check for:

- new users or SSH authorized_keys entries;
- new cron jobs or systemd timers;
- outbound connections to unknown destinations;
- file transfers (scp, sftp, curl, wget).

**Splunk SPL for new authorized_keys:**
```spl
index=linux sourcetype=auditd
| search hostname="<hostname>" path="*/.ssh/authorized_keys"
| table _time exe args pid
| sort _time
```

## Step 5: Escalation decision tree

Use the following decision tree to classify the alert and select the action.

```
START
  |
  v
[Is source IP in approved allow-list?] --YES--> [Is targeted account privileged?] --YES--> [Page on-call within 15 minutes]
  |NO                                                       |NO
  |                                                         v
  v                                                 [Notify asset owner within 1 business day]
[Did success occur after failures?]
  |YES                                     |NO
  v                                         v
[Was success validated by IdP/MFA?]    [Is failure volume above 10 per host in 1 hour?]
  |YES               |NO                |YES                              |NO
  v                  v                 v                                 v
[Monitor]    [Page on-call      [Block source at     [Record false positive
              within 15 min]     perimeter firewall]   and tune threshold]
```

### Decision conditions

| Condition | Classification | Action | Timeline |
|---|---|---|---|
| Approved scanner + documented ticket + non-privileged account | Benign positive | Record owner and ticket; tune only if recurring | Next business day |
| Legitimate user error + matching endpoint + no privilege change | Benign positive | Close with evidence | Next business day |
| External IP + admin account + success after failures | Confirmed intrusion | Page on-call; contain source and session; preserve evidence | Within 15 minutes |
| External IP + non-privileged account + success after failures | Suspicious | Page on-call; review session and commands | Within 15 minutes |
| Internal IP + repeated failures + no success | Attempted intrusion | Block or rate-limit source; monitor targeted accounts | Within 1 hour |
| Failure volume above 10 per host in 1 hour | Distributed attack | Enable host-centric rate limiting; widen investigation | Within 1 hour |
| Source matches known NAT/jump host + 4+ accounts | Benign positive | Suppress or raise spray threshold for that host group | Next business day |
| Internal source + dormant account + success after failures | Credential reuse | Reset credentials; review recent session activity | Within 1 hour |

### Paging criteria

Page the on-call engineer only when **all** of the following are true:

1. The source IP is external or unclassified;
2. The targeted account is privileged, dormant, or shared;
3. A successful authentication occurred after the failures;
4. No approved change ticket covers the activity.

If any condition is false, route to the SOC queue for business-hour review.

## Containment actions

Containment must match organizational authority and impact. Apply the least
disruptive action that stops confirmed or suspected malicious activity.

- Terminate an unauthorized session immediately.
- Block or rate-limit the source IP at the perimeter firewall or cloud
  security group.
- Disable or reset the affected account and revoke active sessions.
- Replace exposed SSH keys and audit `authorized_keys` on all accessible hosts.
- Isolate a compromised endpoint from production networks.
- Preserve relevant logs before retention or rotation removes them.

Avoid permanent source blocking without considering shared VPN, NAT, and cloud
addresses that may affect other users.

## Closure record

Every investigation must produce a closure record with the following fields:

- alert ID and rule;
- analyst name and timestamps (open, triage, close);
- evidence reviewed (raw logs, SIEM queries, TI results);
- source and account ownership;
- related systems and alerts;
- classification and confidence;
- actions taken (block, reset, monitor, suppress);
- false-positive cause and tuning recommendation, if applicable;
- links to supporting evidence (screenshots, exported JSON, ticket numbers).

Store closure records in the ticketing system and review them monthly to refine
thresholds and suppression rules.
