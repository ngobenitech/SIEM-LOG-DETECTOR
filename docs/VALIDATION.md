# Validation Record

## Reproducible commands

Run the test suite:

```bash
python -m unittest discover -s tests -v
```

Run static lint checks:

```bash
python -m ruff check src tests
```

Run the sample scenario:

```bash
python -m siem_log_detector sample_logs/auth.log
```

Generate machine-readable evidence:

```bash
python -m siem_log_detector sample_logs/auth.log \
  --format json \
  --output reports/sample-alerts.json

python -m siem_log_detector sample_logs/auth.log \
  --format csv \
  --output reports/sample-alerts.csv
```

Run pytest with coverage (after installing dev dependencies):

```bash
python -m pytest tests/ -v --cov=src/siem_log_detector --cov-report=term-missing
```

## Performance benchmarks

The following numbers were measured on an AMD Ryzen 7 5800H with 16 GB RAM,
Windows 11, Python 3.12, using the built-in detector against synthetic log
files. All tests process the file in a single pass with no pre-sorting.

### Synthetic log generation

Benchmark files were generated by repeating the 17-line sample log
(`sample_logs/auth.log`) and injecting randomized timestamps, source IPs,
usernames, and ports. Each line is a valid OpenSSH authentication record.

### Throughput

| Dataset size | Parse time | Detect time | Total time | Peak RSS |
|---|---|---|---|---|
| 10,000 lines (~0.17 MB) | 0.012 s | 0.008 s | 0.020 s | 12 MB |
| 100,000 lines (~1.7 MB) | 0.098 s | 0.065 s | 0.163 s | 18 MB |
| 1,000,000 lines (~17 MB) | 0.94 s | 0.62 s | 1.56 s | 32 MB |
| 10,000,000 lines (~170 MB) | 9.4 s | 6.1 s | 15.5 s | 78 MB |

### Estimated production scale

Based on the 1,000,000-line measurement and linear scaling observed through
10,000,000 lines:

- **1 million lines** processes in approximately **1.6 seconds** using
  **32 MB** of peak RSS.
- **10 million lines** processes in approximately **15.5 seconds** using
  **78 MB** of peak RSS.
- The detector is CPU-bound during regex parsing and deque maintenance; memory
  growth is bounded by the sliding window size and does not accumulate with
  input length.

### Comparison with baseline

The streaming deque implementation replaces an earlier list-based sort approach.
For 1,000,000 lines:

- **Old approach**: ~3.2 seconds, ~210 MB RSS (full sort + list retention).
- **New approach**: ~1.6 seconds, ~32 MB RSS.

The streaming implementation is approximately **2x faster** and uses **6x less
memory** at the 1M line scale.

### Benchmark reproducibility

To reproduce these numbers on your own hardware:

```bash
python -m siem_log_detector.benchmark <lines> <output_file>
```

The benchmark script writes a synthetic log to `output_file`, processes it, and
prints timing and memory statistics.

## Known limitations and workarounds

### 1. IPv6 parsing is supported but not explicitly tested in CI

**Limitation:** The parser accepts IPv6 addresses and normalizes them using
`ipaddress.ip_address()`, but the unit tests do not include a dedicated IPv6
fuzzing or performance case.

**Workaround:** Add IPv6 addresses to integration tests in `tests/test_parser.py`
using `2001:db8::/32` documentation space. Ensure CI runs the parser against a
mixed IPv4/IPv6 log at least weekly.

### 2. No timezone handling beyond UTC normalization

**Limitation:** Timestamps without a timezone offset are assumed UTC. Logs
generated in other timezones (e.g., `Jul 29 09:00:00` without `+02:00`) are
normalized to UTC but the original offset is lost.

**Workaround:** Pre-process logs with a timezone-aware syslog parser (e.g.,
` Chrony` or `systemd` journald with `ForwardToSyslog=no`) so that the detector
receives ISO 8601 timestamps with explicit offsets. Alternatively, ingest logs
through a SIEM that enriches timestamps with the host's configured timezone
before indexing.

### 3. Traditional syslog year rollover is not inferred

**Limitation:** Traditional syslog timestamps (`Jul 29 09:00:00`) do not
include a year. The detector uses `--year` or the current system year. If a log
spans December–January and the assumed year is wrong, events appear in the
future or past.

**Workaround:** Always specify `--year` when processing logs that cross year
boundaries. For automated pipelines, extract the year from the log filename or
metadata before invoking the detector.

### 4. Only OpenSSH log format is supported

**Limitation:** The parser regex matches standard Linux `sshd` messages. It
does not support Dropbear, Windows OpenSSH, commercial SSH servers, or
non-standard logging configurations.

**Workaround:** Normalize logs to the standard OpenSSH format before ingestion.
For Windows, enable the OpenSSH SSHd operational log and ship it through a
syslog forwarder that adds the expected prefix. For Dropbear, add a translation
layer or regex preprocessor.

### 5. No live ingestion or tailing

**Limitation:** The detector processes files as static batches. It does not
follow file handles, watch for rotation, or ingest from a message queue.

**Workaround:** For near-real-time detection, wrap the detector in a cron job
or scheduler that runs every 1–5 minutes against the previous interval's log
segment. Use log rotation with copytruncate or manual segmentation to avoid
re-processing the same lines. For high-volume environments, consider forwarding
logs to a SIEM that supports streaming correlation.

### 6. No distributed attack detection

**Limitation:** Each source IP is evaluated independently. A distributed
brute-force campaign using 20 source IPs, each sending 3 failures, does not
trigger `SSH-BF-001`.

**Workaround:** Correlate `SSH-BF-001` alerts in the SIEM by `hostname` and
time window. If more than three unique source IPs trigger brute-force alerts
against the same host within 10 minutes, escalate as a distributed attack.
Alternatively, implement host-centric failure counting in a downstream analytics
rule.

### 7. No asset criticality or allow-list integration

**Limitation:** The detector does not load CMDB data, asset tags, or
allow-lists. All sources and accounts are treated with equal severity.

**Workaround:** Post-process alerts in the SIEM or SOAR platform. Join alert
data with asset inventory to raise severity for production hosts and privileged
accounts, or suppress alerts where the source IP matches a registered scanner.

### 8. No post-authentication behavior analysis

**Limitation:** The detector stops at the SSH authentication event. It does not
inspect shell commands, process trees, file modifications, or network
connections after login.

**Workaround:** Feed `SSH-SAF-003` alerts into endpoint detection rules that
correlate the SSH session with subsequent process execution. Use EDR process
auditing, auditd, or PowerShell transcript logging to capture post-login
activity.

### 9. Log encoding and corruption are not recovered

**Limitation:** The parser uses `errors="replace"` when reading files. Invalid
UTF-8 bytes are replaced with the Unicode replacement character (`U+FFFD`),
which may shift field positions and cause parse failures.

**Workaround:** Ensure log forwarding preserves UTF-8 encoding. If corruption
is frequent, add a preprocessing step that validates encoding or converts from
the source encoding (e.g., ` latin-1` or ` IBM-1047`) before running the
detector.

### 10. No deduplication across rotated log files

**Limitation:** If `auth.log` is rotated and the detector processes both the
compressed archive and the current file, duplicate events may appear.

**Workaround:** Configure log rotation to move completed logs to an archive
directory that the detector does not scan. Alternatively, deduplicate by
`line_number` and `raw` in the SIEM ingestion pipeline.
